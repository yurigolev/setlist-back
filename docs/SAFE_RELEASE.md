# Подготовка безопасного релиза

Эта процедура отделяет проверку копии данных от будущей выкладки. Push/merge в `main` автоматически запускает deploy обоих репозиториев. До готовности production-настроек и назначения владельца выпускать изменения нельзя.

## Проверка копии

Нужен один завершённый согласованный бэкап: `COMPLETE`, `postgres.dump`, `objects/manifest.json` и все перечисленные в манифесте файлы. Можно скопировать уже готовый daily backup с сервера: это не останавливает API. Не объединяйте дамп и файлы из разных бэкапов.

```sh
npm run release:rehearse -- /absolute/path/to/backup /absolute/path/to/new-report.json
```

Команда создаёт отдельный случайно названный Compose-проект с PostgreSQL и MinIO в tmpfs, случайными паролями и свободными loopback-портами. Штатный `.env` и работающие приложения не используются. В пустую БД сначала восстанавливается дамп, затем применяются текущие миграции. Текущий API до восстановления не запускается.

Проверки:

- Хеши и порядок уже применённых миграций совпадают с SQL релиза.
- Все существующие столбцы и строки сохраняются; для каждой таблицы сравнивается SHA-256. Новые столбцы допускаются.
- Известное изменение `0006`: `expires_at` существующих приглашений становится `NULL`. Количество затронутых приглашений явно записывается в отчёт. Новые приглашения бессрочные; при наличии старых приглашений переход нужно отдельно оценить.
- Повторный запуск мигратора ничего не меняет.
- Каждый объект восстанавливается и повторно проверяется по размеру и SHA-256.
- На копии проверяются доступ владельца к старым песням и скачивание всех активных вложений через новый API. Когда владельца ещё нет, используется синтетический аккаунт только внутри одноразовой копии; это не проверка реального Telegram-входа и не выбор production-владельца.
- После проверки доступа ещё раз сравниваются исходные данные и ревизии библиотек, песен и вложений.

При успехе и ошибке удаляется только созданный этой командой проект. При аварийном завершении проверьте `cleanedUp` в отчёте и удаляйте ресурсы только проекта с указанным случайным именем. Бэкап и отчёт остаются локально. Хранить их в `backups/`: каталог исключён из Git и Docker-контекста. Отчёт содержит хеши и агрегаты, без содержимого песен и секретов.

## Настройки перед будущей выкладкой

Приватный фрагмент `.env.telegram.production.local` и ожидаемая identity владельца подготовлены локально. Настройки BotFather и порядок сверки владельца: [TELEGRAM_PRODUCTION.md](TELEGRAM_PRODUCTION.md). Фрагмент содержит только Telegram/PWA/TTL/owner значения; он не заменяет полный серверный `.env.production`.

На сервере в приватном `/opt/setlist/.env.production` должны быть настоящие значения `TELEGRAM_CLIENT_ID`, `TELEGRAM_CLIENT_SECRET`, `TELEGRAM_REDIRECT_URI=https://setlivo.ru/v1/auth/telegram/callback`, `PWA_ORIGIN=https://setlivo.ru`, TTL access/refresh. Callback нужно зарегистрировать для production-клиента в Telegram. Локальный callback не заменяет production callback.

Подготовленные `docker-compose.prod.yml` и `scripts/deploy.sh` необходимо установить на сервер отдельно, до выпуска образов: существующий deploy обновляет только Docker image, не эти файлы. Сохраните текущие серверные файлы и обе предыдущие SHA образов. Проверять Compose командой `docker compose --env-file .env.production -f docker-compose.prod.yml config --quiet`, чтобы не печатать секреты.

Compose требует непустые Telegram credentials и принудительно использует secure cookies. `NODE_ENV=production` также запрещает callback на другом origin или пути. Deploy-скрипт проверяет конфигурацию нового образа отдельной командой до остановки API и бэкапа; эта команда не запускает миграции. Затем штатный backup останавливает записи и сохраняет БД с файлами перед обновлением backend.

Бэкап репетиции не заменяет свежий бэкап непосредственно перед релизом. Если после репетиции изменились миграции или схема источника, повторить проверку новой копии. Не переименовывать Compose-проект `setlist` и тома `pgdata`/`miniadata`.

## Явное назначение владельца старой библиотеки

Назначение не выполняется миграциями, запуском API или первым входом. Сначала выбранный владелец должен войти через настоящий Telegram в обновлённый backend. Его UUID берётся из собственного ответа `/v1/auth/session`; сверяются issuer и opaque `subject` в плане. Username, числовой Telegram profile ID и первый попавшийся пользователь для выбора не подходят.

Следующие команды — для будущего согласованного окна выпуска, после backend и до проверки доступа/выкладки frontend. Сейчас их на production не выполнять. `AUTH_USER_UUID` заменить UUID конкретного проверенного пользователя.

```sh
cd /opt/setlist
install -d -m 700 /opt/setlist/release
docker compose --env-file .env.production -f docker-compose.prod.yml run --rm --no-deps -T \
  -v /opt/setlist/release:/release api \
  node dist/ops/legacy-owner.js plan AUTH_USER_UUID /release/legacy-owner-plan.json
cat /opt/setlist/release/legacy-owner-plan.json
```

`plan` только читает БД и создаёт новый приватный файл. Проверить БД, аккаунт (UUID, issuer, subject), ID старой библиотеки `00000000-0000-4000-8000-000000000001`, название, ревизию и отсутствие конфликтующих прав. План привязан к endpoint, идентификатору PostgreSQL-кластера, OID базы и текущему состоянию библиотеки.

Только после проверки плана:

```sh
docker compose --env-file .env.production -f docker-compose.prod.yml run --rm --no-deps -T \
  -v /opt/setlist/release:/release:ro api \
  node dist/ops/legacy-owner.js apply /release/legacy-owner-plan.json
```

`apply` блокирует старую библиотеку и атомарно создаёт membership `owner` с durable adoption marker. Чужой кластер, неизвестный аккаунт, изменившаяся ревизия, другой ранее назначенный владелец или права без marker приводят к отказу. Изменившееся состояние требует нового плана. Повторное применение тому же аккаунту — no-op; намеренное удаление/понижение прав не отменяется. Для чтения идентификатора кластера нужен доступ к `pg_control_system()`; стандартный пользователь текущего Docker PostgreSQL имеет его. Команда не создаёт `auth_users` и не меняет песни, вложения, object keys или их ревизии.

## Порядок выпуска и откат

Окно обслуживания: свежий согласованный бэкап → backend и миграции → реальный Telegram-вход выбранного владельца → план и назначение → проверка старых песен/файлов владельцем и запрета доступа посторонним → frontend → повторная проверка. Между обновлениями старый клиент может получать `401`; это ожидаемый перерыв доступа. Реальный Telegram-вход остаётся отдельной обязательной проверкой: репетиция копии использует синтетическую идентичность.

Healthcheck подтверждает работоспособность БД/API/хранилища, но не назначение владельца и не реальный Telegram-вход. Откат image не откатывает SQL-миграции. Для возврата до Telegram требуется совместимая пара предыдущих frontend/backend образов. Восстановление БД и MinIO — отдельная процедура при остановленных записях; оно теряет изменения, сделанные после выбранного бэкапа. Не выполнять `down -v` на рабочем проекте.
