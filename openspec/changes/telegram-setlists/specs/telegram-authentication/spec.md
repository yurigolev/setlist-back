## Purpose

Подтверждать пользователя через текущий Telegram OIDC и предоставлять приватную серверную сессию для совместной работы.

## ADDED Requirements

### Requirement: Проверенный вход Telegram

Система SHALL выполнять серверный Authorization Code Flow с PKCE S256, одноразовым state, nonce и привязкой попытки к браузеру; принимать только криптографически проверенные ID tokens с ожидаемыми issuer, audience, nonce и сроком действия. Система SHALL запрашивать только openid и profile.

#### Scenario: Успешный вход

- **WHEN** Telegram возвращает корректный code для активной попытки того же браузера
- **THEN** сервер создаёт сессию и возвращает пользователя на допустимый внутренний адрес приложения

#### Scenario: Подмена или повтор попытки

- **WHEN** подпись, issuer, audience, nonce, state, PKCE, browser binding либо срок недействителен или попытка уже использована
- **THEN** вход отклоняется и сессия не создаётся

### Requirement: Приватная сессия

Система SHALL хранить устойчивую идентичность по issuer/sub, выдавать непрозрачную cookie HttpOnly SameSite=Lax, применять Secure при HTTPS и возвращать безопасный профиль и CSRF token только текущему пользователю. Session/auth ответы MUST иметь Cache-Control no-store.

#### Scenario: Нет активной сессии

- **WHEN** клиент вызывает приватный API без действующей сессии
- **THEN** получает 401 без данных библиотеки и файлов

### Requirement: Защита изменений и выход

Система SHALL проверять разрешённый Origin и CSRF token для изменения состояния. Выход SHALL отзывать серверную сессию и очищать cookie.

#### Scenario: Межсайтовый запрос

- **WHEN** mutation приходит с чужим Origin или неверным CSRF token
- **THEN** сервер отклоняет запрос без изменения данных

#### Scenario: Выход

- **WHEN** пользователь выполняет корректный выход
- **THEN** прежняя cookie больше не даёт доступ к приватным API
