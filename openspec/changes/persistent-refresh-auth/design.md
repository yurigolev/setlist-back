## Context

См. proposal.md. Сейчас `setlist_session` выдаётся на `AUTH_SESSION_TTL_SECONDS=604800`. `PgAuthStore` проверяет `expires_at`; refresh отсутствует. На клиенте `auth.ts` делает прямой fetch сессии/выхода, `sessionTransport.ts` хранит CSRF и callback сброса, `libraryApi.ts` самостоятельно обрабатывает 401. `invalidate()` удаляет личные IndexedDB. В `songs.ts` reconnect повторно проверяет сессию, в `setlists.ts` это делает focus.

Main specs ещё не опубликованы. Поведение 401 в `telegram-setlists/private-offline-cache` конфликтует с новым сохранением данных; новая спецификация определяет замещающее поведение, согласование при sync/archive обязательно.

## Goals / Non-Goals

**Goals:** единый клиентский composable, долгое обновляемое подтверждение пользователя, оффлайн-чтение без удаления библиотеки по времени, сохранение изоляции и серверного контроля прав.

**Non-Goals:** оффлайн-запись, изменение Telegram OIDC, бессрочные refresh, публикация или миграция production без отдельного запроса.

## Decisions

1. Собственные непрозрачные случайные токены в HttpOnly cookies. JWT не нужен: текущий API всё равно проверяет сессию и права через БД. Оставить `setlist_session` как access cookie для совместимости, добавить refresh cookie, ограниченную auth path. TTL: access 900 секунд, refresh 7776000 секунд, скользящий срок после успешного refresh. Cookies и серверные сроки согласованы; refresh без сети невозможен.

2. Серверное семейство refresh с устойчивым ID, userId, CSRF, сроком и историей использованных хэшей. Access ссылается на семейство; отзыв атомарно закрывает access и refresh. `POST /v1/auth/refresh` блокирует семейство, потребляет текущий refresh и выдаёт новые токены в одной транзакции. Историю хранить до удаления семейства. Использованный токен в течение десяти секунд возвращает 409 без выдачи токенов и без отзыва; более поздний replay отзывает семейство. Клиент на 409 проверяет уже обновлённую cookie-сессию, не запускает бесконечные повторы. Это защищает от ложного отзыва при конкуренции; похищенный токен остаётся опасен до обнаружения повторного использования или отзыва.

3. Защита refresh после холодного старта: `GET /v1/auth/session` подтверждает только access; отдельный no-store `GET /v1/auth/refresh-context` возвращает безопасный профиль и CSRF для действующего refresh без продления и выдачи access. `POST /v1/auth/refresh` проверяет точный Origin и этот CSRF. Refresh cookie никогда не авторизует приватный API. Выход проверяет access или refresh с Origin/CSRF и отзывает семейство. Настоящий CSRF mismatch не трактовать как отзыв доступа.

4. `src/composables/useAuthSession.ts` — единственное место для состояния авторизации, session initialization, access/refresh транспорта, CSRF, single-flight, поколения сессии, login/logout и событий вкладок. `auth.ts` — тонкий Pinia facade; `sessionTransport.ts` можно оставить временным re-export без логики. Все приватные API и media используют `authFetch`; `libraryApi` сохраняет парсинг DTO и доменных ошибок, но не принимает решения о refresh. Pinia stores обращаются к фасаду для состояния и публичных действий; reconnect/focus не содержат самостоятельной обработки токенов.

5. Web Locks координирует refresh/выход между вкладками. Получив lock, вкладка проверяет access заново — другая вкладка могла уже обновить cookies. Внутри вкладки один pending Promise. Для браузеров без Web Locks остаются single-flight и серверный короткий 409-сценарий; недоступное восстановление является временной ошибкой, а не причиной удалить кэш. Lock имеет единое имя для origin. Refresh не меняет поколение пользователя, иначе собственный retry станет ложным stale response; logout/account change/отзыв семейства меняют поколение. Перед отправкой повторного запроса и публикацией ответа проверять контекст. Повторять только replayable тела текущего API (JSON/FormData), не произвольные потоки.

6. Разделить `offline` и `reauthRequired`: offline — сеть недоступна; reauthRequired — сервер подтвердил отсутствие действующего refresh. Оба режима блокируют сетевые изменения; последний подтверждённый пользователь и локальные данные сохраняются для чтения. UI показывает повторный вход при reauthRequired, даже когда user присутствует. Access 401 сначала пытается refresh; только окончательный отказ меняет состояние. Network/5xx не меняют идентичность и не стирают кэш. Повторный вход того же userId сохраняет файлы, другого — сбрасывает контекст и очищает прежние приватные данные. Logout и подтверждённые permission refusals сохраняют строгую очистку.

7. На первом обновлении клиента действующую legacy session повышать до семейства отдельным защищённым шагом refresh bootstrap; просроченную legacy session не продлевать. Добавление nullable familyId сохраняет текущие QA fixtures и старые cookies. Не менять TTL уже выданных старых сессий. Нужны серверная миграция и отдельный backend change до client apply; текущий frontend OpenSpec root не разрешает редактировать backend автоматически через свой apply.

## Risks / Trade-offs

- Потерянный ответ ротации может оставить браузеру использованный refresh → короткое окно 409 и повторная проверка access; после окна повторный вход, кэш сохраняется.
- Несколько вкладок, logout и поздний Set-Cookie → единый lock для refresh/logout, проверки поколения и тесты поздних ответов; logout очищает cookies и отзывает семейство после завершения предшествующего refresh.
- Локальное чтение отозванных данных без сети нельзя остановить немедленно → при подтверждённом reconnect права перепроверяются, недоступные scope удаляются. Очистка storage браузером по-прежнему может удалить кэш независимо от авторизации.
- Срок refresh 90 дней означает повторный вход после более долгого отсутствия обновлений → это предсказуемое ограничение, без удаления оффлайн-библиотеки.

## Migration Plan

Подготовить согласованный backend change, nullable связи access с семейством и таблицы refresh; проверить миграции на disposable PostgreSQL. Выпустить backend с legacy bootstrap и новым OpenAPI, затем frontend. Обновить env examples и deployment docs. Для отката оставить добавленные таблицы и старые access-compatible cookies; новая функциональность refresh будет недоступна, повторный вход может потребоваться. Выпуск и production миграции не входят в текущую авторизацию.
