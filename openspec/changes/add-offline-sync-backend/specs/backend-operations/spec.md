## Purpose

Задаёт воспроизводимую серверную эксплуатацию и резервное копирование единственной библиотеки песен и файлов.

## ADDED Requirements

### Requirement: Воспроизводимое окружение разработки

Система SHALL предоставлять документированный способ локально запустить API, реляционную БД и объектное хранилище с изолированными persistent volumes и применёнными миграциями.

#### Scenario: Чистый локальный запуск

- **WHEN** разработчик выполняет документированную команду запуска на чистом окружении с Docker
- **THEN** API, БД и объектное хранилище становятся доступны, а API сообщает готовность через healthcheck

### Requirement: Явный режим публичного API

Система SHALL предоставлять API без регистрации и входа в первой версии. API SHALL явно документировать, что любой клиент с адресом API может читать и изменять библиотеку. CORS SHALL ограничивать только браузерные обращения с иных origin и SHALL не представляться защитой API. Секреты PostgreSQL и объектного хранилища SHALL храниться вне исходного кода.

#### Scenario: Неверный origin

- **WHEN** браузер с недоверенного origin вызывает API
- **THEN** API не предоставляет ему разрешение CORS, но не обещает защиты от прямого HTTP-запроса

### Requirement: Восстановление библиотеки

Система SHALL документировать создание и проверку резервной копии PostgreSQL и объектных данных, достаточных для восстановления связей песен и файлов.

#### Scenario: Проверка бэкапа

- **WHEN** оператор выполняет документированную процедуру проверки восстановления
- **THEN** он может подтвердить доступность песен и связанных вложений в изолированном окружении

### Requirement: Доставка проверенных релизов

Система SHALL проверять релиз основной ветки до публикации и развёртывать конкретный проверенный образ компонента без сборки приложения на VPS. Pull request SHALL не развёртываться в production. Обычная автоматическая доставка SHALL пропускать commit, если основная ветка уже продвинулась; явный ручной откат SHALL оставаться отдельной операцией.

#### Scenario: Успешный push основной ветки

- **WHEN** проверки текущего commit основной ветки успешны
- **THEN** образ этого commit публикуется и доставляется по проверенному SSH, после чего проверяется готовность API

#### Scenario: Ошибка проверки или устаревший commit

- **WHEN** обязательная проверка релиза не прошла или commit уже не является текущим основной ветки
- **THEN** обычный автоматический workflow не заменяет работающий production release этим commit

### Requirement: Сериализация и откат обновлений

Система SHALL сериализовать изменения frontend, backend и создание согласованных backups на одном VPS. Перед backend replacement SHALL создаваться backup текущих DB и objects. Ошибка готовности SHALL приводить к восстановлению предыдущего image/config; система SHALL не представлять это как автоматический откат DB migrations.

#### Scenario: Одновременные обновления

- **WHEN** frontend и backend workflow запрашивают deploy одновременно с backup
- **THEN** операции выполняются по очереди без конкурентной замены общей конфигурации и без несогласованного снимка данных

#### Scenario: Неготовый новый backend

- **WHEN** заменённый backend не проходит readiness check
- **THEN** deploy сообщает failure и пытается восстановить предыдущий образ, сохраняя backup для отдельного восстановления данных при несовместимой миграции

### Requirement: Приватная инфраструктура и секреты

Production SHALL публиковать только необходимые web/administration endpoints; PostgreSQL и object storage SHALL не публиковаться напрямую. Passwords, private keys и backup env SHALL оставаться вне Git, frontend build и публичных артефактов. Автоматический deploy SHALL использовать отдельный доступ с ограниченными административными правами и проверять SSH host identity.

#### Scenario: Прямой внешний запрос к хранилищу

- **WHEN** внешний клиент пытается обратиться напрямую к БД или object storage production VPS
- **THEN** эти сервисы не доступны через опубликованные host ports

#### Scenario: Публикация кода и образов

- **WHEN** код, спецификации и Docker images публикуются в repositories/registry
- **THEN** значения production passwords и private keys не включаются в публикацию

### Requirement: Согласованный перенос DB и файлов

Перенос библиотеки SHALL сохранять DB metadata и бинарные файлы из одного согласованного снимка. До объявления переноса успешным SHALL проверяться изолированное восстановление, связи, число активных записей, размеры и checksums объектов. Исходный снимок SHALL сохраняться вне целевого VPS.

#### Scenario: Перенос локальной библиотеки на свежий VPS

- **WHEN** оператор восстанавливает согласованные DB и object backups в явно выбранное свежее production окружение
- **THEN** активные песни, вложения, revision и checksums соответствуют исходному снимку, а source volumes не удаляются

### Requirement: Регулярное резервное копирование

Production SHALL автоматически создавать согласованные private backups DB и object files с ограниченной retention и SHALL сохранять configuration, необходимую для recovery. Наличие копий только на целевом VPS SHALL не считаться выполненным off-server recovery requirement; регулярный вынос и проверка новых copies должны подтверждаться отдельно.

#### Scenario: Ежедневная копия

- **WHEN** наступает время production backup
- **THEN** записи кратко приостанавливаются, создаётся DB/object/config snapshot, после чего API снова запускается и сохраняются последние семь complete copies

#### Scenario: Копии только на VPS

- **WHEN** автоматический вынос за пределы VPS ещё не настроен
- **THEN** эксплуатационный статус явно показывает это ограничение и не объявляет защиту от полной потери VPS завершённой

### Requirement: Готовность постоянного HTTPS-origin

Постоянный production origin SHALL использовать валидный TLS certificate с автоматическим продлением, перенаправление HTTP и same-origin API. Readiness SHALL проверять реальную доступность API, а не только HTTP redirect. Включение TLS SHALL не менять data volumes и SHALL не представляться авторизацией.

#### Scenario: Переход после публикации DNS

- **WHEN** выбранный домен корректно делегирован на production VPS и оператор включает HTTPS
- **THEN** PWA, API snapshot и content доступны по защищённому origin, HTTP перенаправляется, сертификат валиден, а DB и objects сохранены

#### Scenario: Редирект без доступного API

- **WHEN** web proxy перенаправляет HTTP, но API не готов
- **THEN** production readiness не считает один успешный redirect подтверждением работоспособности приложения
