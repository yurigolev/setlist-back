## Context

Исходный минимальный Fastify backend уже развит в API одной библиотеки с PostgreSQL 16, MinIO, миграциями и полным снимком. Frontend в соседнем репозитории использует backend как источник истины и IndexedDB как подтверждённую копию. На 2026-10-06 выполнен HTTP production-деплой и перенос текущих локальных PostgreSQL/MinIO; прежние браузерные тестовые записи временного origin не импортировались. См. мотивацию в `proposal.md` и ниже фактический контекст эксплуатации.

## Goals / Non-Goals

**Goals:**

- Сделать сервер единственным источником данных, а IndexedDB — проверенной локальной копией для офлайн-чтения.
- Сделать серверный контур понятным для изучения: явные SQL-миграции, API-контракты, Docker-окружение и приватные файлы.
- Сделать повтор сетевого запроса безопасным, а синхронизацию полного снимка воспроизводимой.
- Сохранить в схеме место для будущей привязки библиотеки к пользователю без реализации аккаунтов сейчас.

**Non-Goals:**

- Не реализовывать регистрацию, вход, сессии, роли и нескольких пользователей.
- Не принимать офлайн-правки: без сервера PWA открывает последнюю синхронизированную копию только для чтения.
- Не обещать фоновую синхронизацию, когда PWA выгружена iOS.
- Не добавлять outbox, журнал событий, cursor, CRDT, дедупликацию медиа или трансформацию изображений.
- Не публиковать MinIO/S3 и не выдавать постоянные публичные URL файлов.

## Decisions

### TypeScript/Fastify, PostgreSQL, MinIO и Docker Compose

Существующий Fastify-сервис развивается внутри текущего backend-пакета. Docker Compose запускает API, PostgreSQL и MinIO с именованными volumes; локальные учётные данные и порты вынесены в `.env`, а не остаются в compose-файле. Это даёт один понятный стек для Mac и VPS.

Fastify выбран вместо NestJS: меньше скрытой магии и слоёв для небольшого API, но остаются схемы входных данных, плагины и тестируемые маршруты. Express отклонён: он не даёт столь же стройной типизированной валидации по умолчанию. Drizzle выбран для миграций и запросов: SQL остаётся обозримым; Prisma отклонена как более тяжёлая абстракция для учебного небольшого backend.

### Схема одной библиотеки

Постоянные сущности: `libraries`, `songs`, `attachments`. При миграции создаётся одна библиотека с постоянным `library_id`; песни и вложения ссылаются на него. Позже `libraries` можно связать с таблицей пользователей и фильтровать запросы по владельцу без изменения идентификаторов песен. Таблиц пользователей, сессий, мутаций и событий сейчас нет. У песен есть UUID, `revision`, серверные даты; у вложений — UUID, MIME, размер, checksum и неизменяемый object key. Отдельная `library_revision` увеличивается в той же транзакции, что и каждое подтверждённое изменение метаданных.

Удаление убирает запись из активной библиотеки. Старый клиент не может восстановить её своей устаревшей правкой, поскольку изменения требуют актуальной ревизии. Долговременные tombstone не нужны: клиент обновляет полный снимок, а не получает историю событий.

### Публичный API прототипа

В первом релизе нет регистрации, токенов и проверки пользователя. API публичен как на текущем HTTP IP, так и на будущем постоянном HTTPS-адресе: знание адреса достаточно для чтения и изменения библиотеки. Это принято для рабочего однопользовательского прототипа; CORS ограничивает только запросы из браузеров и не защищает API от прямых HTTP-запросов. MinIO и PostgreSQL не публикуются напрямую, их учётные данные вынесены из репозитория. Авторизация и разделение библиотек по пользователям оформляются отдельным change позже.

### Запись на сервер и получение снимка

Клиент выполняет `POST /v1/songs`, `PATCH /v1/songs/:id` и `DELETE /v1/songs/:id` только при наличии сети. Создание принимает стабильный ключ идемпотентности, чтобы повтор после потери ответа не дал дубликат. `PATCH` и `DELETE` передают известную ревизию песни через `If-Match`; устаревшая ревизия отклоняется. При конфликте клиент получает актуальный снимок, показывает пользователю, что данные изменились, и не перезаписывает их автоматически.

`POST` и `PATCH` принимают только текстовые поля песни; массив `attachments` не является входом этих маршрутов. Загрузка и удаление файлов выполняются отдельными запросами, поскольку файл передаётся потоком и может требовать повтора независимо от текста. Одна кнопка сохранения в PWA последовательно выполняет необходимые запросы, показывает частичный успех при сбое и обновляет локальный снимок после завершения. Если сервер подтвердил хотя бы один шаг, клиент получает актуальный снимок даже при ошибке следующего шага.

После каждого успешного изменения и при запуске с сетью клиент запрашивает `GET /v1/library/snapshot`; есть и ручная кнопка обновления. Ответ содержит полный список песен и доступных вложений одной зафиксированной ревизии библиотеки. Для объёма текущего MVP полный снимок проще и надёжнее event cursor: клиенту не нужно восстанавливать пропущенные события или хранить outbox. Параллельные серверные записи после формирования снимка попадут в следующее обновление.

### Локальная копия и офлайн-доступность

IndexedDB хранит только подтверждённый сервером снимок и Blob-файлы из него. Клиент повторно использует Blob с тем же attachment id и checksum; недостающие файлы скачивает через API и проверяет размер/checksum. Новые метаданные и `library_revision` публикуются в локальной базе только после успешного получения обязательных файлов; песни, отсутствующие в новом снимке, удаляются из локальной копии в одной транзакции. Сетевые загрузки проходят до этой транзакции через временную область хранения. При сбое клиент удаляет временные объекты и оставляет предыдущий полностью пригодный снимок. Очистка уже не используемых файлов выполняется после публикации нового снимка.

Когда сервер недоступен, PWA открывает последнюю сохранённую копию и позволяет поиск, просмотр изображений и воспроизведение MP3. Создание и редактирование требуют сети; локально сохранённая, но не подтверждённая правка не появляется. Тестовые данные на старом временном origin не импортируются: первая постоянная библиотека создаётся через сервер.

### Загрузка и удаление вложений

`POST /v1/songs/:songId/attachments` принимает файл и стабильный `attachmentId` для повтора. Backend проверяет размер, сигнатуру и MIME, потоково кладёт объект в приватный bucket, затем в транзакции создаёт метаданные и увеличивает ревизию библиотеки. Публикация происходит только после успешного завершения обоих шагов. Повтор с тем же id и checksum возвращает прежнее вложение, а с другими байтами — конфликт. Если метаданные не зафиксированы, лишний объект удаляется или ставится на очистку.

Сервер допускает несколько изображений и один активный MP3 на песню, как текущая PWA. Замена MP3 состоит из двух операций: сначала подтверждённое удаление прежнего, затем загрузка нового. Если вторая операция не удалась, снимок честно показывает песню без MP3; клиент предлагает повторить загрузку и не заявляет, что вся форма сохранена.

Загрузка проверяет, что песня ещё существует и её ревизия не изменилась с момента отправки. Если песню удалили за время передачи, вложение не публикуется. При отмене запроса результат может быть неизвестен клиенту, поэтому он запрашивает снимок и удаляет вложение отдельным запросом, если оно успело сохраниться. `DELETE /v1/attachments/:id` удаляет вложение из активной библиотеки; объект очищается после фиксации метаданных. `GET /v1/attachments/:id/content` выдаёт содержимое только для активного вложения. Эти маршруты не требуют входа в прототипе.

### Контракт и ограничения API

Валидация запросов ограничивает поля, размер файлов и длину текстовых значений. Ошибки имеют единый формат `code`, `message`, `requestId`; ошибка конфликта возвращает актуальную ревизию. OpenAPI описывает маршруты и статусы. CORS разрешает постоянный origin PWA, но не заявляется средством защиты. Лимиты файлов задаются конфигурацией; конкретные значения фиксируются перед реализацией upload и отражаются в `.env.example` и OpenAPI.

## Risks / Trade-offs

- [Публичный API позволяет посторонним читать и менять библиотеку] -> это принято только для прототипа; перед хранением чувствительных данных нужна отдельная авторизация.
- [После подтверждённой записи клиент не смог обновить IndexedDB] -> серверная запись остаётся успешной, UI показывает ошибку обновления копии и повторяет получение снимка при следующем запуске или вручную.
- [Обрыв сети при загрузке MP3] -> клиент повторяет запрос с прежним attachment id; если результат неизвестен, сверяется со снимком сервера.
- [Ошибка между MinIO и PostgreSQL] -> объект не виден в снимке, а лишний файл очищается; бэкап охватывает обе системы.
- [Квота IndexedDB или скачивание файла сорвали обновление] -> предыдущий рабочий снимок сохраняется, ошибка показывается пользователю.

## Migration Plan

1. Добавить серверные миграции, API песен и файлов; проверить работу чистой библиотеки в PostgreSQL и MinIO.
2. Подключить клиент в соседнем репозитории к API: успешная запись на сервер, затем получение снимка и файлов в IndexedDB. Не переносить тестовую библиотеку временного origin.
3. Проверить два устройства: запись на первом, обновление на втором, затем офлайн-просмотр и воспроизведение на обоих.
4. Для публикации настроить постоянные HTTPS-origin, CORS, секреты PostgreSQL/MinIO и бэкап с проверкой восстановления. Публичность API остаётся явным ограничением прототипа.
5. При откате frontend использовать последнюю сохранённую локальную копию только для чтения. Миграции БД откатывать лишь совместимым способом без удаления пользовательских данных.
